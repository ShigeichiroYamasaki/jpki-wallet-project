# クラウド利用体験版

パスキーでログインし、本人確認の模倣を経てウォレットを接続するWebアプリを実装しました。利用者によるターミナル操作やサーバー起動は不要になる構成です。画面の公開先は既存のGitHub Pagesです。APIの配置・接続は未完了のため、現時点では準備中の画面になります。

## 公開先

- トップページ：<https://shigeichiroyamasaki.github.io/jpki-wallet-project/>
- 利用画面：[プロトタイプを開く](/prototype/index.html)
- パスキーのRP ID：`shigeichiroyamasaki.github.io`
- WebAuthnの検証対象Origin：`https://shigeichiroyamasaki.github.io`
- API：別のHTTPSエンドポイント（未配置）。GitHub Pagesは静的配信のためAPIを実行できません。

プロトタイプではcacanet.orgとそのサブドメインを使用しません。GitHub Pagesのオリジンは同じアカウントの他リポジトリのPagesと共有されるため、それらも信頼境界に含みます。パスキーはリポジトリのパス単位には分離されません。

## 利用の流れ

1. ウォレット拡張のある通常のブラウザで公開URLを開く。
2. 初回はパスキーを登録し、続けてログインする。
3. PFによる本人確認の成功応答を模倣する。
4. ウォレットで接続メッセージに署名する。
5. 任意で合成作品の操作にパスキー・ウォレット両方で署名し、証拠ファイルを保存する。

実本人確認、実権利移転、送金は行いません。スマホの本人確認アプリとの連携は未実装です。法的整合性は専門家による精査が必要です。

## 構成

GitHub Pagesの画面 → 別HTTPSエンドポイントのNode.js認証API → 永続SQLiteの単一インスタンス構成です。Docker用定義を用意しています。パスキーとウォレットの秘密鍵は利用者の認証器・ウォレットで扱い、サーバーへ送信しません。

利用者ごとにパスキーの所有者を分け、未ログイン時には登録済みパスキーからアカウントを識別します。セッション・模倣結果・ウォレット署名・証拠は利用者間で共有しません。合成人物は共通の試験データで、実人物の一意性を示しません。

現在はブラウザ拡張ウォレット向けです。モバイルウォレット接続・アカウント復旧・複数サーバーへの横展開は未対応です。公開オリジンを変更するため、localhostの試験で使用したパスキーは再登録が必要です。

## ローカル版との関係

[ユーザPCの実カード試験](/mac-prototype)は従来通り利用できます。クラウド版にはカードリーダー操作やPIN入力機能を置きません。将来の実本人確認は連携先APIが提供する検証結果・証拠を確認して設計します。

管理者向けの配置・制約はリポジトリの `services/cloud-prototype/README.md` を参照してください。既存の共有VMは以前の負荷問題を踏まえ、配置先の容量と接続経路を確認してから利用します。

## 接続設定

管理者がAPIに `PUBLIC_ORIGIN=https://shigeichiroyamasaki.github.io`、`APP_PATH=/jpki-wallet-project/prototype/`、`API_ORIGIN=実際のAPIのHTTPSオリジン` を設定します。GitHub Actionsのリポジトリ変数 `JW_API_ORIGIN` に同じAPIオリジンを登録してPagesを再ビルドします。未設定時にローカルAPIへ接続することはありません。

APIは許可Originを完全一致で検査し、CORSのプリフライトに応答します。別オリジン構成ではCookieを使わず、有効期限付きセッショントークンをJavaScriptメモリだけに保持します。再読み込み後は再ログインとなります。APIのURLをクエリ文字列や利用者入力から切り替える機能は設けません。

Google提供のHTTPS URLを利用する場合も、データ永続化を確認して配置します。現在のSQLiteとメモリセッションを、そのままCloud Runの一時ファイルシステムと複数インスタンスで運用する構成にはしません。
