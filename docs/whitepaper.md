## 1. 要旨

JPKI Wallet Projectは、音楽クリエイターと利用者が、音楽サービスの運営や資金配分に参加するための認証基盤を研究・開発するプロジェクトです。NPO法人による提供を構想し、本人確認、日常のログイン、ウォレットによる意思表示を、それぞれに適した仕組みで扱います。

設計の中心は、JPKIによる本人確認、FIDO2／パスキーによる継続認証、Ethereumウォレットの署名を、同じ参加登録の意思に結びつける「鍵束縛プロトコル」です。個人の生データをブロックチェーンに公開せず、ガバナンスに必要な参加資格を確認することを目指します。

初期の評価対象は100人規模の音楽Web3ガバナンス実験です。まず合成データと模倣PFで技術・操作・運用の課題を検証し、実サービス化の判断材料を公開します。100人は登録規模の目標であり、現時点の収容実績や同時処理能力ではありません。

JPYCを利用する音楽サービスでは、発行・償還の手続きに加え、誰がどの作品について何を操作できるかを確認する必要があります。本認証サービスの価値は、確認された本人・ウォレット・権限・同意の関係を継続して管理し、クリエイターの権利保護と利用者の利便性を支えることです。[JPYC EXとの役割分担と存在意義](#jpyc-service-value)を第3.1〜3.6節に整理します。

本書はプロジェクトの目的と設計判断を関係者間で共有する資料です。投票制度、音楽の権利処理、資金配分の実装を完成済みとするものではなく、技術仕様の詳細は仕様書と追加設計を参照します。

## 2. 解決したい課題

### 2.1 ウォレットの数と参加者の数を区別する

ウォレット署名で確認するのは、そのアドレスを操作できることです。一人が複数のウォレットを持てるため、アドレスの数をそのまま参加者の数と扱う設計では、重複参加への対策が必要になります。本プロジェクトは、本人確認に基づく参加資格を導入し、同一人物による重複登録を抑止する仕組みを検証します。

ただし、本人確認だけで名義貸し、鍵の共有、共謀、アカウント譲渡まで防げるとは考えません。「一人一票」を採用するか、クリエイターと利用者の権限をどう分けるかは、認証とは別のガバナンス設計です。

### 2.2 確認の厳格さと使いやすさを両立する

参加のたびに本人確認を求めると、利用者の負担が大きくなります。初回登録や復旧など、本人確認が必要な場面と、通常の継続認証を分けます。署名時には何を登録・承認するのかを説明し、処理途中の失敗や再開方法を利用者が理解できる画面を目指します。

### 2.3 個人情報の開示を必要な範囲に抑える

音楽コミュニティで参加資格を確認するために、氏名や住所を他の参加者へ公開する必要はありません。本人確認に必要な情報と、参加資格の照会に必要な情報を分け、保存量と共有先を絞ります。ハッシュ化した識別子であっても、他の情報との照合可能性は残るものとして設計します。

## 3. NPOの役割と責任

NPOには、参加資格の運用、利用者への説明、問い合わせ・復旧対応、委託先管理、仕様と検証結果の公開を担う役割を想定します。認証基盤の運営主体と、音楽サービスの運営主体との責任分界は、実サービス化前に明確にする必要があります。

| 関係者 | 想定する役割 | 確定・検証が必要な事項 |
| --- | --- | --- |
| NPO | 認証サービスの運用、同意管理、鍵束縛、資格状態・復旧手続の管理 | 法的位置付け、委託契約、管理者権限、事故対応体制 |
| PF事業者 | 将来の実JPKI検証の委託先 | 対応機能、利用条件、識別子の継続性、障害時の照会方法 |
| クリエイター・利用者 | 登録、パスキー認証、ウォレットによる意思表示、実験への評価 | 対応端末、操作説明、参加条件、辞退・削除の手続 |
| 音楽サービス運営者 | サービス運営、参加資格を使った投票等の提供 | 権利処理、資金管理、投票ルール、認証基盤との責任分界 |
| 開発・レビュー担当 | 実装、試験、設計変更の記録 | セキュリティ評価、法的精査、運用継続性 |

原ADRでは、NPOがSPとしてPFへ検証を委託する方針と、PocketSign Verifyの採用方針を記録しています。本書ではこれを設計上の選択として扱い、契約済み・接続済みとは扱いません。民間事業者によるJPKI利用の制度は、[デジタル庁の案内](https://www.digital.go.jp/policies/mynumber/private-business/jpki-introduction)を参照し、具体的な提供形態に応じて確認します。

NPOであることだけで中立性が保証されるわけではありません。資格の停止・復旧、管理鍵の変更、委託先の変更について、判断権限、記録、異議申立ての手続を整えることを運用上の課題とします。

### 3.1 JPYCを利用するサービスにおける存在意義 {#jpyc-service-value}

本認証サービスは、JPYCによる決済を利用する人と、その人が音楽サービス内で行使できる権限との関係を、検証可能にする基盤を目指します。本人確認、パスキーによる継続認証、ウォレットとの鍵束縛、権利・委任の証明を組み合わせ、「誰が、どの立場で、何に同意して操作したか」を記録します。

JPYCの取得・償還が便利になっても、対象作品の権利者、代理人の権限、収益配分先の変更への同意は、音楽サービス側で確認する必要があります。本サービスの中心的な価値は、本人確認を繰り返すことではなく、本人・鍵・権限・同意の関係を継続して管理することにあります。

単にJPYCを保有・送受信するだけの用途では、本認証サービスを追加する価値は限定的です。著作権、収益配分、代理操作、ガバナンスなど、主体と権限の関係が重要な用途を主な対象とします。すべてのJPYC利用者に本サービスの導入を必須とするものではありません。

### 3.2 eKYC・JPKI・JPYC EXの役割分担

eKYCはオンラインで本人確認を行う手続きであり、JPKIはその本人確認に利用する手段の一つです。本人確認の技術的成功と、事業者が必要な取引時確認を完了したという判断は区別します。本節のJPYCは円への償還が可能な電子決済手段を想定し、JPYC Prepaidとは区別します。

| 領域 | 担当・役割 | 本サービスとの境界 |
| --- | --- | --- |
| JPYC EXの利用手続き | JPYC側が必要な本人確認・審査、発行・償還の最終受付・確定を担う | NPOの認証成功をJPYC側の審査完了と扱わない |
| 本人確認 | 将来の実JPKI等により利用者の本人性の根拠を得る | 現在の仮想カードは模倣。本人確認だけで作品の権利保有を確定しない |
| パスキー認証・鍵束縛 | 登録利用者の継続認証と、ウォレットとの対応関係を確認する | ウォレット署名だけで法的な本人情報や包括的な操作権限を証明しない |
| 権利・委任の確認 | 権利の確認主体が契約等の根拠を審査し、サービスが操作を認可する | 認証基盤のNPOが当然にすべての権利を審査できるとはしない |
| 操作への同意・証拠 | 対象と条件を固定した操作への承認を記録する | ログインを将来の送金・権利操作への包括的同意として使わない |

「ウォレットがeKYC済み」という一括した状態ではなく、確認者、対象サービス、対象主体・アドレス、確認方法、日時、有効期限・失効状態を区別する設計とします。JPYC残高や入金履歴から、そのアドレスの現在の利用者がJPYC EXで本人確認済みだと推定しません。

### 3.3 JPYC EX連携APIで補える利用体験

公開されている連携機能には、JPYC EXのアカウント連携、発行・償還画面への案内、アドレス登録の補助、手続後の画面表示に使う状態情報があります。審査や申込みの確定はJPYC側で行うと説明されています。[開発元の公式発表（2026年7月13日）](https://www.simplex.inc/news/2026/3581/)

本システムへの組み込み案は、利用者がパスキーでログインし、ウォレットを接続した後、「JPYCを用意する」からJPYC EXへ進み、手続後に音楽サービスへ戻る流れです。クリエイターには「JPYCを円に戻す」入口を用意する案を検討します。送金・残高照会・チェーン上の入金確認は別の機能として設計し、手続画面から戻ったことだけで入金完了と表示しません。

APIのアカウント連携が、本人確認結果の第三者への提供や再利用まで認めるとは仮定しません。KYC状態・本人情報・署名付き証明の提供範囲、NPOでの再利用条件、テスト環境、利用審査・費用、認証方式、返却される状態の意味は、JPYCへの確認事項です。JPYC EXとのアカウント連携だけでは、本サービスのJPKI鍵束縛が成立したことにもなりません。

正式に再利用が認められる場合は、その結果を本人確認の根拠として受け入れる構成を検討します。取得していない本人確認結果をNPOが補完して「JPYC確認済み」と証明する設計にはしません。

### 3.4 具体例：売上の受取先ウォレットを変更する

新しいウォレットの署名だけでは、その署名者に対象作品の売上受取先を変更する権限があるかは分かりません。本サービスでは、次の手順を将来の設計例とします。

1. 登録利用者をパスキーで認証し、アカウントの停止・復旧状態を確認する。
2. 対象作品に対する権利・委任の根拠と、受取先を変更できる権限・有効期間を確認する。
3. 新しいウォレットの署名により、その鍵を利用できることを確認する。
4. 対象作品、変更前後の受取先、適用条件、nonce、有効期限を含む変更内容に対して、操作別の承認を得る。
5. 検証結果、承認内容、適用結果を記録し、必要な通知と異議申立ての導線を設ける。

これは音楽サービス上の受取先変更であり、JPYC EXの登録アドレス変更を自動で代行することを意味しません。権限の確認が取れない場合は変更を保留します。本人確認だけで権利の保有は分からないため、契約の審査、権利登録、訂正・失効、紛争時の対応を別途整備します。

### 3.5 DID／VCと第三者検証の位置付け

主体識別子は、鍵の変更履歴も含めてサービス内の主体を識別するために用います。DIDの方式は未選定であり、全サービスで追跡可能な共通識別子の公開を前提としません。VC等の証明は、本人確認、鍵束縛、作品別の権利・委任を分け、発行者と証明範囲を明示します。

JPYCから正式に証明が提供される場合も、出所・利用条件・有効性を保って参照し、NPOが行った確認と区別します。アカウントの連携情報だけを、JPYCが発行した本人確認VCへ読み替えません。検証できない状態は「未確認」または「判断不能」として扱います。

DID／VCの採用だけで、法定本人確認の代替、著作権の真実性、電子署名法上の推定効が自動的に成立するとは考えません。また、決済以外のウォレット利用すべてにDID／VCが法的に必須であると主張するものでもありません。第11節の証拠基盤と組み合わせ、第三者による事実関係の検証を支援する設計目標です。

### 3.6 プロトタイプで検証する範囲と本番化の条件

現在のプロトタイプでは実カードを使用しない方針を維持します。仮想カードの模倣、実際のパスキー認証・ウォレット署名、JPYC EXとの連携状態、権利審査の状態を別々に表示・管理します。仮想カードの成功を実JPKI本人確認済みと表示せず、JPYC EXは未連携として扱います。

次の検証案は、仮想カード、パスキー、ウォレット接続に続けて、JPYC EXの模擬手続きとテスト用トークンの支払い体験を設けることです。この追加案は未実装であり、実際のJPYCの発行・償還やeKYCの成立を示しません。

本番化前には、JPYCとの利用条件・責任分界に加え、NPOが実際に持つ資産移転権限や売買・交換への関与、本人確認結果の共有、権利審査と証拠保存を専門家と精査します。非営利という組織形態や技術的な鍵束縛だけを、法令適合性の根拠にはしません。

## 4. 三つの役割を結ぶ設計

| 仕組み | 確認する対象 | 単独では確認しないもの |
| --- | --- | --- |
| JPKI | 初回登録等での公的な本人確認 | 日常の全操作が同じ人によるものか、音楽の権利保有者か |
| FIDO2／パスキー | 登録した認証資格による継続認証 | 公的な本人性、ウォレットの操作権限 |
| Ethereumウォレット署名 | 対象アドレスを操作する権限と署名内容 | 自然人の一意性、包括的な資金移転の承認 |

WebAuthnは公開鍵の登録と認証を分けて扱う標準です。本設計でも最初にパスキーの公開鍵を登録し、その後の認証に使います。パスキーの同期可能性を考慮し、一つの物理端末にしか存在しないと仮定しません。[W3C WebAuthn](https://www.w3.org/TR/webauthn-2/)

ウォレット連携にはSIWE（Sign-In with Ethereum）を採用する方針です。署名の検証に加え、要求元、nonce、有効期限、アドレス、chain ID等を照合します。SIWEの署名を送金承認や個々の投票への同意と同一視せず、それぞれの操作に必要な承認を別に定めます。[ERC-4361](https://eips.ethereum.org/EIPS/eip-4361)

### 同じ登録意思への束縛

三つの検証が別々に成功するだけでは、対象の取り違えを防ぐ要件として不十分です。追加設計では、セッション、期限、利用サービス、対象ウォレット、チェーン、パスキー公開鍵等をまとめた `BindingIntent` を固定し、各検証の証拠をその内容に対応させる案を示しています。

```text
登録の意思を固定する（BindingIntent）
           │
     ┌─────┼─────┐
     ▼     ▼     ▼
    JPKI  Passkey  Wallet
     └─────┼─────┘
           ▼
      NPOによる照合
           ▼
    束縛レコードの受付
           ▼
   チェーン確定・資格反映
```

この図は将来の論理構成です。現在の模倣APIが三つの鍵を束縛しているわけではありません。また、PFの本人確認成功応答を、任意の `BindingIntent` へのJPKI署名と同一視しません。必要な署名対象を実PF・SDKで扱えるかは実接続前の確認事項です。

## 5. 想定する利用体験

1. **目的と条件を確認する。** 保存する情報、公開される情報、資格の有効範囲、辞退・復旧方法を説明し、同意の版を記録します。
2. **パスキーを登録する。** 未登録の公開鍵を使って認証が完了したことにせず、候補の登録と検証を行います。
3. **本人確認とウォレットの結合を行う。** 同じ登録意思に対応する証拠を検証します。プロトタイプの本人確認は合成データによる模倣です。
4. **処理状態を確認する。** サーバーでの受付と、チェーンへの記録確定を分けて表示します。確認が取れる前に有効資格を付与しない設計です。
5. **参加し、必要に応じて変更・辞退する。** 継続認証後に、サービス側のルールに従って参加します。端末紛失、ウォレット変更、資格停止、削除は別の手続として整備します。

登録操作への同意を、将来のすべての投票・配分への包括的な同意として使わないことを原則とします。JPKIを利用できない人や対応端末を持たない人の参加方法は未決定であり、参加対象の制約と代替導線を実験前に検討します。

## 6. プライバシーとデータの取扱い

基本方針は、検証のために一時利用する情報と、運用上保存する情報を分けることです。次の表は実サービスに向けた設計方針であり、現在のP0に業務データベースが実装されていることを示しません。

| 情報 | 方針 |
| --- | --- |
| 氏名・住所・生年月日・性別、JPKI証明書・署名値 | 実接続時もDB・ログへ永続保存しない方針。現在の模倣APIでは実データを受け付けない |
| 利用者識別子 | 生IDの代わりに、サービス固有の秘密値を使うHMAC等の派生値を検討 |
| パスキー公開鍵・ウォレットとの対応 | 必要な範囲でオフチェーンに保存し、アクセスを制限 |
| 監査イベント | 結果・時刻等の限定的なメタデータ。原ADRの1年保持案は目的・法的根拠とともに再確認 |
| オンチェーン情報 | 束縛のコミットメント、資格照会に必要な識別子・アドレス対応を最小化して設計 |
| 秘密鍵・シークレット | 利用者の秘密鍵をサーバーへ集めない。サーバーの送信鍵・管理鍵は権限と用途を分離 |

ハッシュやHMACを使っても匿名性や法令適合が自動的に成立するわけではありません。同じサービス内での照合、ウォレットの公開履歴との関連付け、秘密値の漏えい等を評価します。HMACの秘密値やPFを変更する際も、同一人物性が自動的に維持されるとは仮定しません。

オフチェーンの削除と、オンチェーンの資格失効は別の処理です。公開チェーンに残る過去の記録は後から消去できない前提で、記録する項目の妥当性を先に検討します。利用者の同意だけで問題が解消するとせず、法的精査の対象とします。

ログ、監視、バックアップも同じ保存方針に含めます。メモリ上の参照を破棄することと、物理メモリの即時消去を保証することを区別します。実験終了時の削除計画は未確定であり、原ADRが参照するADR-018を今後整備する必要があります。

## 7. セキュリティと信頼の境界

本構想は、NPOのバックエンドによる検証と資格登録を信頼するモデルです。ブロックチェーンに記録することだけで、登録前の本人確認が正しかったと独立に証明されるわけではありません。

| リスク | 設計・検証の方針 |
| --- | --- |
| 別の登録や署名の流用 | nonce、期限、対象ウォレット、サービス、署名対象を照合 |
| 重複登録・並行操作 | DBの一意制約と資格台帳で整合性を保ち、同時登録を試験 |
| 再送・途中停止 | 冪等キー、入力一致確認、DB outboxによる未完了処理の追跡 |
| PF・チェーンの結果不明 | タイムアウトを成功／失敗と断定せず、照会・保留・手動確認へ移行 |
| 管理鍵の侵害 | 権限分離、登録数・頻度の制限、停止・ロール失効の手続を設計 |
| 端末紛失・鍵共有 | 復旧時の再確認、旧資格の無効化、通知と異議申立てを設計 |
| 誤認や排除 | 不利益な資格判断の説明とレビュー手続を設ける |

これらは今後の実装・検証課題を含みます。サーバーの送信鍵が侵害されれば不正な資格登録につながるため、ガス代残高を小さくするだけでは対策になりません。運用者の権限と緊急停止・復旧を含めた評価が必要です。

以下は2026年9月7日時点の記録です。

| 項目 | 状況 |
| --- | --- |
| 公開資料 | VitePress／GitHub Pagesで仕様書・ADR・追加設計を公開 |
| Docker基盤 | API、worker、PostgreSQL、リバースプロキシを実装 |

| 模倣の識別 | `provider: mock`、`isMock: true`、`assurance: simulation-only` を明示 |

| テスト | ローカルとGitHub Actionsで模倣API・不正入力拒否等を検証済み |

プロトタイプは実PFへ接続せず、実証明書と基本4情報を入力しません。模倣で成功しても、公的な本人確認やPF製品との互換性を検証したことにはなりません。

クラウドはGoogle Cloudの既存e2-microと標準ディスクを共有する方針です。新しいVM、公開IPv4、Cloud NATは追加していません。プロトタイプの入口はlocalhost限定で、一般参加者用の公開サービスではありません。無料枠対象の構成でも請求額ゼロを保証せず、同居試験の結果を踏まえて軽量化と資源配分を再検討します。既存の音楽サービスは稼働を継続しています。

## 9. 100人規模の実験と評価

実験の目的は、参加者が理解して登録・認証・変更・辞退できるか、重複登録や障害を安全に扱えるか、運用負担が継続可能かを確かめることです。

| 段階 | 取り組み | 次の段階へ進む条件 |
| --- | --- | --- |
| P0 基盤・PF模倣 | 実装済みの模倣APIを維持し、クラウド構成を再検討 | 既存サービスへの影響を抑えた安定稼働を確認 |
| P1 模擬登録フロー | パスキー登録・認証、SIWE、束縛状態管理を実装。PFは模倣 | 差替え・再送・期限切れ・重複登録を拒否できること |
| P2 端末・障害検証 | 対応端末、ウォレット、模擬チェーンからテストネットへの移行を検証 | 端末上の一連の操作、障害・復旧・資格失効を確認 |
| P3 模擬100人実験 | 合意した参加方式で10→30→100人へ段階的に拡大 | 操作と運用の評価、情報管理・終了時削除計画を確認 |
| 将来の実サービス化 | 必要な場合に実PFを接続 | 契約・制度上の手続・法的精査・セキュリティ評価を別途実施 |

評価指標には、登録完了率、所要時間、離脱した手順、問い合わせ件数、復旧成功率、資格状態の誤表示、重複登録の拒否、費用と運用時間を含めます。応答時間やメモリ・ディスク余裕も測定し、目標値と実測値を分けて公開します。

人数を増やす前に参加者のアクセス方式と対応端末を確定します。現在の開発者向けSSH接続を、そのまま100人へ配布する計画ではありません。実験中もPFは模倣であり、参加者を「JPKI本人確認済み」とは表示しません。

## 10. 法的精査と持続可能な運営

本プロジェクトでは、**認証基盤の法的整合性は専門家による精査が必要**であることを公開の前提とします。特に次の論点を、提供するサービスの具体的な範囲と併せて確認します。

- JPKIの利用形態、SP／PFの役割、必要な手続、契約と再委託の条件。
- 取得・派生・公開する情報の法的位置付け、利用目的、保存期間、第三者提供、国外での処理・保存。
- オンチェーンの不可逆性、削除・失効・復旧、同意と説明の設計。
- NPO、認証の委託先、音楽サービス運営者の責任分界、事故時の対応と利用者救済。
- 音楽の権利処理、資金配分、税務等、認証以外のサービスに付随する事項。

本書は法的判断を示すものではありません。原ADRに含まれる制度・製品・料金の説明も、導入時点の条件で再確認します。

運営費にはクラウドだけでなく、将来のPF利用料、問い合わせ・復旧対応、監査、法的精査、バックアップと事故対応を含めます。負担方法、利用料金、継続予算は未確定です。本書では独自トークンの発行・販売、投資収益、クリエイターへの確定した配分率を定めません。

## 11. 将来の拡張と公開検討

### 第三者が検証できる認証・権限の証拠基盤

鍵が暗号学的に結びついても、JPKIの法的効果がウォレットへ承継されたり、後続のすべての操作が本人の意思によると証明されたりするわけではありません。追加方針として、主体識別子とVC、操作ごとの署名、監査証拠を組み合わせ、電子文書の本人帰属の立証を支援します。

| 要素 | 役割 |
| --- | --- |
| DID等の主体識別子 | サービス内で本人と鍵履歴を対応付ける。方式は未選定 |
| 本人確認VC・鍵束縛VC | 誰をどの方法で確認し、どの鍵を登録したかを発行者が証明 |
| 作品別の権利・委任VC | 対象作品、権限範囲、期間、契約等の根拠を区別して証明 |
| 操作ごとの二重承認 | 同じ操作文書をFIDO2認証とウォレット署名に結び付ける |
| 証拠パッケージ・検証ツール | 第三者が署名、主体対応、権限、時点の有効性、実行結果を検証 |

初回は「この鍵を本サービスで自分の操作に使う」という登録意思を記録します。重要な権利操作では、作品、相手方、許諾条件、実行先、nonce、期限を固定して再度承認します。SIWEログインを権利操作への包括的同意とはしません。

VC発行者の実在性・証明権限・鍵履歴を台帳で確認します。NPOの署名が正しいことと、利用者の意思や権利内容が真実であることを分けます。PFの署名付き証跡が得られない場合、第三者はNPOの証明と監査に依拠する範囲が残ります。

証拠には操作文書、両署名、VC、過去時点の状態情報、NPO受付証、タイムスタンプ候補、実行結果を含めます。暗号化した証拠庫へ保存し、本人情報や契約原文を公開チェーンに置きません。現在の非保存方針と証拠保存の関係、保存期間・開示・削除を実データ導入前に確定します。

この方式は**電子署名法3条の推定効を主張する前提事実の立証を支援する設計目標**です。推定効や法令適合性が認められた方式ではなく、専門家の精査が必要です。政府Q&Aは事業者署名型電子契約を対象としており、本方式への直接の承認ではありません。[政府Q&A](https://www.digital.go.jp/assets/contents/node/basic_page/field_ref_resources/517ca59b-6ea4-4179-a338-8d1b51a4d40b/4ae659c2/20240109_digitalsign_qa_01.pdf)

まずPF模倣のVCと操作署名・証拠出力・検証ツールを追加する計画です。これらは未実装であり、模倣を実JPKIや実権利の証明に使用しません。VCの有効性等を確認できない場合は「判断不能」とし、「法的推定効あり」という自動判定は行いません。

詳細は[仕様16節](/specification#evidence-design)、[ADR-020](/adr#adr-020)、[ADR-021](/adr#adr-021)を参照してください。ゼロ知識証明による選択的開示は引き続き将来の研究課題です。

仕様変更はADRで理由と影響を記録します。本書は原仕様書を上書きする規範文書ではなく、追加設計の提案と実装済みの範囲を整理したものです。矛盾が残る項目は実装・契約前に解決します。特にPFの任意ダイジェスト署名、識別子の継続性、秘密情報管理、実験終了時の削除は未確定事項です。

検討への参加や指摘は、[GitHubリポジトリ](https://github.com/ShigeichiroYamasaki/jpki-wallet-project)で資料を確認したうえで、[Issues](https://github.com/ShigeichiroYamasaki/jpki-wallet-project/issues)に寄せられます。公開の場には本人確認書類、証明書、秘密鍵、個人情報を書き込まないでください。実験参加者の募集開始を示すものではありません。
